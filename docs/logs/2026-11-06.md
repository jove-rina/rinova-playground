## 二、今天的判断性结论

| 问题 | 结论 |
|---|---|
| 13 万行会不会拖垮性能 | 不会拖页面也不会拖构建：字段展开耗时在噪声内，浏览器只收 68KB。被拖垮的是 AI 上下文（单次 2.3MB 输出） |
| 该修文件还是修输出 | 两个都要，但优先级相反于直觉：文件的根因是「外部类型被展开」，输出的根因是「没有预算」。只修文件，`TaoPageTemplate` 仍吐 45KB |
| 字段集去重表（fieldSets） | **不做**：外部声明规则生效后重复只剩边角料，而它会把 manifest 契约改成引用表，UI / MCP / verify 全要跟着动 |
| 清单按组件分片 | **不做**：修完 1.59MB，分片是为还没出现的问题付复杂度；触发条件写进文档（单文件 >5MB 或组件 >1500） |
| 单次响应要不要硬截断 | **不硬截**：`TaoPageTemplate` 120 个 props 的 31.6KB 每行都是真实 API；把字段相关的部分压到 0.7KB 已经消除主要噪音 |
| 手册要不要带契约 | **不带**：合并版 644KB ≈ 29 万 token，模型读不完；契约按组件用 MCP 取 |
| 缩进 JSON 还有用吗 | 没有：`.playground` 是 gitignore 的构建产物，`generatedAt` 也保证它不该被 diff 审视；要读用 `jq` |

## 三、踩坑记录

1. `compare at > rel.length` 判不出行号 → `locate()` 命中时返回 `rel:7`，`:` 的下标正好等于 `rel.length` → 改成 `>=`，否则 `← L<n>` 全空（`verify:mcp` 的行号断言直接红）。

4. `pnpm -s` 在 pnpm 12 上不存在（`unexpected argument '-s'`），别再写。
5. Hermes 的 terminal 会把含 `vite` 的命令判成长驻服务 → `cp -r .../playground-vite` 直接拒跑；用 `ls -d playground-vit*/` 取到变量再 `cp`。
6. LSP 对 `scripts/*.ts` 的即时诊断是**单文件 tsc**（没有项目 tsconfig），会冒一堆 `import.meta` / `no default export` 假错，以 `pnpm typecheck` 为准。

## 七、页内顺序修正（20:00，0.8.1）

用户实机发现：`/_playground/tao-form/form` 的右侧索引里 `event-validate` 在 Props 组下面，正文里它却排在 `model` 上面。

- 根因：插件 `scenes.sort((a,b) => a.order - b.order || a.id.localeCompare(b.id))` 只看 `order`；真实宿主里每个 section 各自从 10 开始编号，撞车后按 id 字母序 —— `event-validate` < `model`，于是 Events 跳到 Props 前面。右侧索引是按 `SECTION_ORDER` 分组的，两边用了两套顺序。
- 修法：新增 `packages/playground-vite/src/scene-order.ts`（`SECTION_ORDER` / `isSection` / `compareScenes` / `orderScenes`），插件扫描末尾改用 `compareScenes`：**分组序 → order → id**。
- 同类问题一起修：`SceneDescriptor.section` 改可选，未声明 section 的场景按 `props` 计入索引（此前它出现在正文却从右侧索引消失）；`PlaygroundPageIndex` / `PlaygroundSceneSection` 都按 `props` 兜底。
- 验收：`verify` 新增「页内场景排序」4 条用例（跨 section 撞车 / 概要永远最前 / 未声明归 Props / 组内 order→id），`pnpm verify` **70/70**。
