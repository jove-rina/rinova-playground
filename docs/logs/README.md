# 工作日志

每天的工作汇总放在这里，文件名 `YYYY-MM-DD.md`（当天收工时写，一天一个文件）。

## 为什么写

- 隔几天回来看能快速恢复上下文：**做了什么、为什么这么定、踩了哪些坑**；
- 用户会按天回溯，所以按时间顺序、按主题分块，不要写成提交列表；
- 结论优先：判断性的取舍（“为什么不用 X”）比过程更有价值。

## 写法约定

1. 开头三行：范围、结论（验证通过数）、代码状态（是否未提交 / HEAD 提交）。
2. 「做完的事」按主题分块，每块给**可核对的数字**（文件路径、行数、像素、毫秒、通过数）。
3. 「判断性结论」用表格：问题 → 结论，方便日后翻案时有据可查。
4. 「踩坑记录」写现象 → 根因 → 解法，一条一行，不要只写现象。
5. 结尾写「下次接着做」，列成可勾选的清单。
6. 只写当天真实发生的事；没验证的不要写成已完成。

## 模板

```markdown
# YYYY-MM-DD 工作日志

> 范围：<今天做的主线>
> 结论：`pnpm verify` x/x、`pnpm typecheck` / `pnpm build` 状态
> 代码状态：N 个文件未提交（HEAD <sha>）

## 一、今天做完的事
### 1. <主题>
- 改动点（文件:行）
- 实测数字

## 二、今天的判断性结论
| 问题 | 结论 |

## 三、踩坑记录
1. 现象 → 根因 → 解法

## 四、规模与验证
- 页/场景数、verify 通过数

## 五、下次接着做
- [ ] ...
```
